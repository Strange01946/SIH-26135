SIH26135 asks for consent-based tracking of what happens after skills training. The candidate, enrollment and assessment records establish the link to later employment. Follow-up surveys capture outcomes such as work, wages, apprenticeships and barriers to placement when an employer record alone cannot tell the full story. The provider import and data quality workflows help keep those records usable across programmes. [SIH26135 problem statement](https://sih2026.ankus.dev/en/ps/SIH26135)

## Screen-to-endpoint contract matrix

Paths below are relative to `/api/v1`. JSON responses use the project's `ApiResponse<T>` envelope unless a binary response is indicated. List routes marked paged use zero-based pagination. This inventory covers the screens reviewed in these six phases.

| Phase and screen | Backend methods and routes | Data, permissions and important behavior |
| --- | --- | --- |
| 30.1 Shared client | Vite proxies `/api` and `/actuator` to localhost:8080 | Axios supports normalized errors, envelope metadata, cancellation, and binary downloads. Each request and refresh carries a UUID correlation ID. TanStack Query retries transient reads. Local proxy requests preserve Spring's cross-origin checks for other origins. |
| 30.2 Login, session and route guards | `POST /auth/login`, `POST /auth/refresh`, `GET /auth/me` | Login takes `usernameOrEmail` and `password`. Refresh takes `refreshToken` and returns the backend's token pair. `/me` returns current roles and scope. The SPA clears credentials and cached data at sign-out. The backend has no logout or token revocation endpoint. Demo account selection prefills usernames on loopback when `VITE_LOCAL_DEMO=true`. |
| 30.3 Trainee profile and training | `GET /trainees?userId=` and `/trainees/{id}`, `GET /training-enrollments?traineeId=`, `GET /attendance-records?traineeId=` | The profile lookup returns one user-linked trainee. Enrollments are paged and attendance is a list. Backend owner scope applies. Enrollment records provide the course, batch and centre labels. The centre response has no contact phone or email. |
| 30.3 Consent | `GET /consents?traineeId=`, `POST /consents`, `PUT /consents/{id}/status` | Trainees can act on their own records. Grants capture purpose, policy and channel. Revocation updates the existing consent record. Employment follow-up and employer sharing correspond to `EMPLOYMENT_FOLLOW_UP` and `EMPLOYER_SHARING`. |
| 30.3 Trainee assessment and certificate | `GET /assessment-results?traineeId=`, `GET /certifications?traineeId=`, `GET /certifications/{id}/download` | The owner-scoped results and certificates are paged. Certificate downloads return `application/pdf` and the frontend checks the PDF signature. The results DTO provides scores and a verdict. It supplies no grading scale or grade value. |
| 30.3 Employment history and recommendations | `GET /analytics/summaries/trainee-outcomes?traineeId=`, `GET /trainees/me/employment-history`, `GET /workflows/skill-gap-remediation/profile?traineeId=`, `POST /workflows/skill-gap-remediation/recommendations/{id}/accept` or `/reject` | The summary provides status and outcome counts. The paged self-service history derives identity from the session and returns work dates, engagement type, starting pay and verification status. Recommendation reads validate trainee scope. Recommendation actions accept a trainee ID and remarks and check ownership. |
| 30.3 Follow-up surveys | `GET /trainees/me/followup-surveys`, `GET /trainees/me/followup-surveys/{taskId}`, `POST /trainees/me/followup-surveys/{taskId}/responses` | `ROLE_trainee` and linked profile required. The trainee sees eligible campaign assignments and the 20 most recent submissions. Submission takes the questionnaire version and typed answers. The backend validates consent, ownership, question types, required answers and available options. It persists the response and completes the task in one transaction. Closed or repeated submissions return 409. The separate `/survey-responses` route requires staff authority. |
| 30.4 Training locations and historical references | `GET /training-centers`, `GET /courses` | Tenant-scoped centres require `center.manage`. Historical course reads require `course.manage`. Providers use Venue Bookings to request a shared centre or propose a temporary location. The usual lists are paged and an exact code returns a single resource. |
| 30.4 Training requirements and batches | `POST /training-requirements/government`, `POST /venue-bookings`, `POST /venue-bookings/{id}/review`, `GET /training-batches`, `PUT /training-batches/{id}/status` | Reviewers publish requirements within their jurisdiction. Providers apply to deliver government training or enter their own skills when requesting a venue. Venue approval creates the batch and its internal outcome reporting references. Batch reads and status updates follow provider scope and require `course.manage`. |
| 30.4 Enrollments and attendance | `GET /trainees?registrationNumber=`, `GET/POST /training-enrollments`, `POST /attendance-records` | Trainee lookup is a single record. Enrollments are paged. Writes require `enrollment.manage` and backend scope. Seat and duplicate conflicts come from the server, and the frontend refreshes availability after a conflict. |
| 30.4 Bulk import and quarantine | `POST /import-batches`, `POST /import-batches/{id}/process` and `/recover`, `GET /import-batches/{id}/status`, `GET /import-batches/{id}/quarantine` and `/quarantine/export` | The upload uses multipart part `file` and query parameters `entityType` and `sourceSystem`. CSV, JSON and NDJSON are staged before processing. Processing is a synchronous backend call with progress observed through an independent status request. Recovery requires confirmation that the worker has stopped. Closing the monitor cancels status requests. The backend has no server-side cancellation route. Quarantine is paged and the authenticated export returns CSV. |
| 30.5 Data quality | `GET /provider/data-quality/issues`, `GET /provider/data-quality/issues/{id}` and `/events`, `POST /provider/data-quality/issues/{id}/investigate`, `/resolve`, `/dismiss`, `POST /provider/data-quality/re-evaluate` | Backend provider scope applies. Issue results are paged and filterable by backend codes. Enrollment corrections use `GET/PUT /training-enrollments/{id}` and send only fields the provider changed. Issue resolution uses `resolutionNotes` in its own request, then refreshes the queue and scorecard. |
| 30.5 Centre scorecard | `GET /provider/centers/{centerId}/scorecard` | Provider-scoped authoritative cleanliness, issue counts, and dropout and completion rates. Missing ratios are displayed as unavailable. |
| 30.6 Assessor schedule and scoring | `GET /assessor/assessments`, `GET /assessor/assessments/{id}` and `/roster`, `POST /assessor/assessments/{id}/draft` and `/finalize` | The assessor sees assigned batches and their rosters. Score entry sends trainee and enrollment IDs, attendance and score components. The server applies the configured pass threshold, validates the full roster and controls finalization. Failed or absent candidates receive no certificate. |
| 30.6 Certificate issuance | `POST /assessor/assessments/{id}/issue-pending`, `GET /certifications/{id}/download` | The assessor workflow can issue certificates on finalization or on eligibility recheck. Issuance also checks training completion, attendance and accredited issuing body. A passing result can remain pending. Download is authorized by result ownership or assessment assignment. |

## Training centre management

The provider workspace uses the affiliated provider on the signed-in account. The admin workspace uses a paged provider directory and exact provider-code lookup. The centre code, name, provider, state or union territory, district, and operational status are required. The shared centre registration and editing forms require a six-digit PIN code. The edit API can retain a valid PIN code already on file. The UI reads districts from the existing geography catalog and lifecycle options from the backend reference table.

Centres with training history retain their district and remain in the directory when made inactive. Removal of an unused centre sets its deletion timestamp. New batches require an active centre. These rules preserve the provider and district links used to compare training outcomes in SIH26135. [SIH26135 problem statement](https://sih2026.ankus.dev/en/ps/SIH26135)

## Public registration and onboarding

| Form | Required from the applicant | Optional in the form |
| --- | --- | --- |
| Candidate | Username, email, password and confirmation, first name, gender response, state or union territory, district, PIN code, and core processing consent | Middle and last names, date of birth, mobile, address, and current employment status |
| Training provider | Provider name, registration or NSDC number, authorised contact name, state or union territory, district, PIN code, account username and email, and password and confirmation | Alternate contact email and contact phone |
| Employer | Company name, authorised contact name, state or union territory, district, account username and email, and password and confirmation | CIN or registration number, GSTIN, alternate contact email, and contact phone |

Password confirmation runs in the browser. Each required location pair is validated against the active geography directory on the server. Candidates can choose “Prefer not to say” for gender. An omitted employment status is stored as `UNKNOWN`. Candidate registration writes one `DATA_PROCESSING` grant alongside the account and trainee profile in the same transaction. Follow-up, employer sharing, and communication have separate permissions. [Phase 29.2 workflow rules](../phase-29/phase-29-2-cross-workflow-orchestration-transaction-choreography-report.md)

The backend reuses the account email when the application omits an alternate contact address. Organisation applications remain pending until an authorised administrator approves them and links the account to its organisation. State administrators can review applications from organisations in their assigned state or union territory. District officers can review applications from organisations in their assigned district. The backend enforces jurisdiction for lists, details, approvals, and rejections. Public tracking shows a masked contact email. Accreditation and employer verification follow their own workflows.

## API inventory and demo configuration

The Spring OpenAPI all-APIs export at the time of review contained 297 unique paths and 439 method/path operations. Spring supports separate mappings on the same method and path with different query parameters. OpenAPI represents those mappings with one method/path operation. The number 677 in the earlier phase brief was not used as the exported contract count. The refreshed export is the input to `npm run generate:types`.

Enable `VITE_LOCAL_DEMO=true` and use the frontend through `http://localhost:5173` to show the demo account selector. It requires separately provisioned accounts and passwords. The trainee survey demo requires an open survey, an active follow-up campaign, a scheduled task linked to the signed-in trainee and active employment follow-up consent.
